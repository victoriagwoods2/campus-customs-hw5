Ticket 102 would have been simpler as one agent with both the Facilities and the Accounting tools. The job was a fixed sequence: read the lease and due date, check available cash, and file a rent payment request. The multi-agent run used three agents, two hand-offs, 10 model requests, and 18,491 tokens, and looked up the same lease three times. One agent with get_ticket_102_lease_and_rent_due_date, get_cash_status, and request_payment_approval could do it in three or four calls. The team earned its cost on ticket 101, where stock, a vendor block, a payment, and a customer message involved three different areas of the shop.

4. Three new problems this team could solve with the tools we built

  1. The October rent notice. Lease 1 is now due 2026-10-02. Facilities would read the lease with get_ticket_context and compare the due date with desk.date_today. Accounting would check get_cash_status. With only $160.00 in checking, request_payment_approval would refuse the $2,400.00 request rather than overdraw the account.   2. A size question about hoodies. If Yale AI Club asked whether they could take size L instead of M, Inventory could use lookup_inventory on CC-HOOD-NAVY and find 14 in L and 6 in XL. Customer Service could then save a reply with save_customer_message_draft based on those confirmed numbers.
  3. Restocking the Crest Mug. CC-MUG-CREST has 0 in stock. Inventory could use list_vendors to find Elm City Gifts (mugs and small goods, 3-day lead time, no unpaid invoices). Accounting could file request_purchase_order_approval, and a person could approve it on the dashboard. This would use the purchase-order path, which none of the three tickets needed.

One caveat: each problem would need a new row in tickets, and the backend's run route currently accepts only tickets 101–103 (DESK_TICKET_IDS). Widening that list is a one-line change. The agents and MCP tools would not need to change.

Evidence: Cash tab (ending balance $160.00), the 101 and 103 ticket tabs, and inventory, vendors, and leases in the working database

5. Three new problems this team could not solve with the tools we built, and what it would need

  1. Actually ordering stock and receiving it. The team can propose a restock, but approve_purchase_order_request only marks a proposal “approved for manual follow-up”. Nothing contacts the vendor, tracks a shipment, or increases inventory.qty when goods arrive. This is why the tee for ticket 101 was never reordered.

    Would need: human-approved submit_purchase_order, track_shipment, and receive_stock tools, backed by new purchase_orders and shipments tables, plus a Procurement agent (or an expanded Inventory role) to follow orders through.

  2. Approving a discount and pricing an order. The team can recommend a price, as it did on ticket 103, but no tool writes to pricing, and there is no table for customer orders or quotes, so an approved $52.20 price has nowhere to go.

    Would need: an orders/quotes table, a create_quote tool, and a human-only approve_price_override tool. A Sales or Merchandising agent would handle the request, with Accounting checking the margin against pricing.unit_cost.

  3. Returns and refunds. The database has no sales, order, or return records, and the system models no incoming revenue. So the team cannot confirm that a customer bought something, record a return, or refund the money.

    Would need: lookup_order, record_return, and a human-approved request_refund_approval tool. Customer Service would handle the customer, Accounting the refund, and Inventory would put returned items back into stock.
